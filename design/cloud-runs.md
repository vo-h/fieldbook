# Cloud runs

Status: Built; checked end to end on AWS (CPU and GPU) and RunPod (GPU) · Last updated: 2026-10-09

`fieldbook run --on remote` runs the same run on a rented machine: the machine runs the same `fieldbook run` as the laptop, with the laptop's run ID, code snapshot, and seed, so records and lineage match local runs ([runs.md](runs.md)). Data is read from and written to the bucket ([storage.md](storage.md)), and runs log to the shared tracking database ([tracking.md](tracking.md) §1). Code: `fieldbook/launch/cloud.py` and `skypilot.py`, `fieldbook/images/`, `fieldbook/clouds/`.

## 1. Decisions

| Decision | Choice | Reason |
|---|---|---|
| Machines | A SkyPilot cluster per run, deleted when the job ends (`sky launch --down`) | No idle machines to pay for; every run starts from a clean machine with its own code |
| Spot instances, managed jobs | Not used | Without spot, preemption is not an issue and hardware failures are rare. A failed run is continued by a new run from its checkpoints (§8) |
| Environment | An image per environment (not per run), tagged by a hash of what defines it; code comes from the snapshot at start-up | Code changes every run, the environment rarely: images are reused across runs, and a code change never triggers a build |
| Building images | Automatically, on a CPU cloud machine started by SkyPilot and deleted after; `fieldbook build --local` uses local Docker | Not limited by the laptop: native architecture, and the multi-GB push stays inside the cloud network |
| Dockerfile | Generated by `fieldbook`; extra system packages via the `image_apt` setting | No Dockerfile to maintain |
| Registry | AWS ECR | Same cloud and region as the bucket and the machines |
| Credentials sent to jobs | Only what the platform needs, automatically; others with `--secret NAME` | The fewer secrets leave the laptop, the better |
| Clouds | AWS and RunPod (images built on AWS, data in S3) | AWS is in use; RunPod is cheapest for GPUs. Both checked end to end |
| Checkpoints | `PLATFORM_CHECKPOINT_DIR` in the bucket per run; a new run continues from a checkpoint's path | Frameworks read the path from user code; the bucket outlives the machine |
| Cost per run | From the cloud's own records, by machine ID (§10) | SkyPilot's totals are wrong for clusters that delete themselves |

## 2. A remote run

```
fieldbook run --on remote [--gpus A100:1] [--cloud aws|runpod] [--nodes N] [--secret HF_TOKEN] [--no-build] train.py --lr 0.1
fieldbook run --on remote torchrun --nproc-per-node 4 train.py      # several GPUs (§9)
fieldbook run --on remote task.yaml                                  # `resources`, `num_nodes` from the task
fieldbook run --on remote train.py --ckpt s3://bucket/vision/checkpoints/<run>/last.ckpt   # continue (§8)
fieldbook build [--local]                   # build the environment image ahead of time
```

| Step | Where | What happens |
|---|---|---|
| 1. Checks | Laptop | The storage root is a bucket, otherwise stop with an explanation; without a shared tracking database, a warning (MLflow runs on the machine are lost when it is deleted). `uv lock --check`. Symlinks pointing outside the repository are refused |
| 2. Prepare | Laptop | Run ID; code snapshot (uploaded to the bucket if new); environment tag (§4) |
| 3. Image | Laptop → registry | If the registry has no image with the tag, build it (§5) and say why ("`uv.lock` changed"); `--no-build` stops instead |
| 4. Launch | Laptop → SkyPilot | A task with `image_id: docker:<image>@<digest>`, `resources` from flags or the task file, the settings and run context as variables, credentials (§7), `--down` |
| 5. Set up | Cloud machine | Download the code snapshot; install the project itself if it is a package (seconds) |
| 6. Run | Cloud machine | `fieldbook run` with the given run ID and no new snapshot: environment record of this machine (Python, packages, CUDA driver, image digest), seed, bootstrap. Datasets in the bucket; MLflow to the shared database |
| 7. Finish | Cloud machine, then laptop | The cluster deletes itself. Its cost is recorded later, from a laptop, from the cloud's records (§10) |

The laptop can sleep or disconnect after step 4. `fieldbook` prints the cluster name (`fieldbook-<run-id>`); `sky logs`, `sky status`, and `sky down` work on it.

## 3. Code, and where cloud differences live

The run's code is its snapshot (runs.md §4), as for local runs; SkyPilot's `workdir` sync is not used, so the code that ran is exactly the recorded snapshot. A project that is itself a package (e.g. a `src/` layout) is installed from the snapshot at start-up; the image holds only its dependencies.

Cloud differences live in `fieldbook/clouds/`, one module per cloud, as in SkyPilot's `sky/clouds/`. `aws.py` holds everything AWS-specific (IAM roles and members' groups, ECR logins, bucket regions, keys for machines off AWS, instance IDs, CloudTrail costs); `runpod.py` holds pod IDs and billing. Each has `machine()` and `cost()`. The rest of the code is cloud-neutral and calls these; launching machines is SkyPilot's and reading buckets fsspec's. Adding a cloud means a module there, with tests against the real service.

## 4. Environment tag

A hash of everything the image is built from: `uv.lock`, the Python version, the base image (pinned by digest), `image_apt`, the platform, the generator's version, and fieldbook's own source. The same tag means the same image; any change means a new one.

| Situation | What `fieldbook` does |
|---|---|
| `pyproject.toml` changed without `uv lock` | Stop: "run `uv lock` first" |
| A package installed locally (e.g. with `pip`) is not in `uv.lock` | Warn before launching: it will not be in the image |
| No `uv.lock` | Stop with an explanation |

## 5. Images

Layers, bottom to top, so that common changes rebuild little:

| Layer | Contents | Rebuilt when | Size |
|---|---|---|---|
| 1. Base | Ubuntu (Debian-based, required by SkyPilot), uv, `image_apt` packages | Base or system packages change | Small |
| 2. Heavy packages | PyTorch with its NVIDIA CUDA packages and Triton, at the versions in `uv.lock`: the entry for the image's system when the lock has one per system (CPU-only PyTorch), from the package's own index before PyPI | PyTorch's version changes | Several GB |
| 3. Other packages | `uv sync --frozen` for the rest | Any other package changes | Usually small |

- **fieldbook in the image:** the exact local fieldbook goes in as a wheel (built from a source checkout, or packed from the installed files), never installed from PyPI by name, since the bootstrap and lineage need the same code on both sides. `uv sync` skips fieldbook (`--no-install-package`).
- **Build machine:** a CPU instance launched with SkyPilot (`sky launch --down`) on `build_cloud`, with Docker; it builds, pushes, and is deleted. About $0.02–0.05 per build. Images are for x86-64 machines, which cloud runs use.
- **Cache:** layers are reused across builds through the registry (`--cache-from`/`--cache-to type=registry`), since the build machine is deleted each time.
- **Format:** images are built without attestations and with Docker media types (`--provenance=false --sbom=false`, `oci-mediatypes=false`). An OCI index with provenance attestations stalled twice in SkyPilot's pull during testing (cause unproven); this format has not.
- **SkyPilot requirements:** Debian-based images; on RunPod, the default `/bin/bash` entrypoint. Generated images run as root with no entrypoint.
- **Cleanup:** images cost about $0.10 per GB-month in ECR, and every change of environment (during development, of fieldbook itself) pushes a new one. `fieldbook log rm --old` deletes those not pushed or pulled for 30 days, with old runs' checkpoints (runs.md §22).

## 6. Settings

In the project file, or `FIELDBOOK_<NAME>` ([projects.md](projects.md) §2):

| Setting | Meaning |
|---|---|
| `image_registry` | Where images go, e.g. `123456789012.dkr.ecr.us-east-1.amazonaws.com/vision` (the repository is created if missing) |
| `image_base` | Base image (default: an Ubuntu image) |
| `image_apt` | Extra system packages, e.g. `["ffmpeg"]` |
| `build_cloud` | Where build machines run: `aws` or `aws/<region>` (RunPod pods cannot run Docker builds) |
| `remote_cloud` | Default for runs: `aws`, `aws/<region>`, or `runpod` (overridden by `--cloud` or the task file) |
| `launch_timeout` | Minutes before a launch that has not started is torn down (default 15) |
| `budget_run_usd` | Most one cloud run may cost; sets its time limit (§11). Project file only. |
| `budget_monthly_usd` | Most the project's cloud runs may cost in a month (§11). Project file only. |

## 7. Credentials and machine roles

| Credential | How the job gets it |
|---|---|
| Bucket access on AWS | The machine's IAM role; no keys copied |
| A machine role that no longer matches the settings | The launch is refused until `fieldbook init` updates the role. Its policy names the storage a machine may reach and the machines it may delete, so under an old policy a paid machine can outlive its run (seen on AWS: after machines were renamed, two could not delete themselves) |
| Database login (`PGUSER`, `PGPASSWORD`) | Sent automatically (the password as a secret) |
| Registry login (ECR, 12 hours) | Fetched on the laptop, sent as SkyPilot secrets: build machines push with it, run machines pull with it |
| Bucket keys on RunPod | The laptop's AWS keys (environment, `~/.aws`, or SSO), sent as secrets; temporary keys expire, so long RunPod runs need long-lived keys |
| Anything else (`HF_TOKEN`, `WANDB_API_KEY`, ...) | Only with `--secret NAME` |

Values come from the environment or `.env`; they are passed as SkyPilot secrets (redacted in its dashboard, not written into the task), never on a command line, and masked in recorded commands as locally. Their names go in `FIELDBOOK_SECRETS`, so the machine's run masks them too.

**Machine roles.** Without a role, SkyPilot copies the laptop's AWS credentials to every machine. With one, a machine gets only what it needs. One pair of roles per AWS account and project, named by a hash of the project's folder and registry:

- `fieldbook-run-<hash>`: objects in the project's folder of the storage root only, and deleting its own `fieldbook-*` instances (SkyPilot's teardown runs on the machine: it looks up the cluster's instances, VPC, and security groups, and terminates them);
- `fieldbook-build-<hash>`: deleting its own instances only.

Neither role has registry permissions. `fieldbook init` shows the policies and creates or updates the roles after asking; launches stop if a role is missing, and go ahead with a warning when the person's credentials may not read IAM (a member whose roles the owner created). SkyPilot does not allow `aws.remote_identity` in a task, so each launch passes a one-cluster mapping in its own project config (`SKYPILOT_PROJECT_CONFIG`), leaving the user's SkyPilot settings untouched. Members' own AWS permissions are in [sharing.md](sharing.md) §3.

## 8. Checkpoints

Each run gets `PLATFORM_CHECKPOINT_DIR = <root>/<project>/checkpoints/<run-id>/` in the bucket, so checkpoints outlive the machine. A run that fails or is cancelled is continued by a new run given the old checkpoint's path (Lightning: `trainer.fit(model, ckpt_path=...)`); the new run's recorded command links them.

## 9. Several GPUs and nodes

`fieldbook run --on remote torchrun ...` uses the same passthrough as local runs (runs.md §2): every rank gets the seed. Multi-node runs set `num_nodes` (`--nodes` or the task file); `torchrun`'s node rank, node count, and master address come from SkyPilot's variables (`SKYPILOT_NODE_RANK`, `SKYPILOT_NUM_NODES`, `SKYPILOT_NODE_IPS`). Only rank 0 saves dataset versions and logs to MLflow, as locally.

**Choosing GPUs.** `--gpus` is SkyPilot's own `accelerators` syntax, passed through, so a GPU can be named or described, and supply that comes and goes (RunPod's) needs no searching first:

| `--gpus` | Means |
|---|---|
| `A10G`, `RTX4090:2` | That GPU, that many |
| `24GB+`, `48GB+:2` | Any GPU with at least that much memory (`24GB`: exactly) |
| `nvidia:24GB+` | The same, of one maker |
| `RTX4090,24GB+` | Several of the above, tried in the order given (SkyPilot's ordered list) |

`--max-price USD` is SkyPilot's `max_hourly_cost`: machines dearer than that an hour are left out. SkyPilot launches the cheapest candidate that has capacity and moves to the next when one has none; nothing of this is fieldbook's code. Before launching, `fieldbook run` lists the candidates with their prices from SkyPilot's catalog (`skypilot.candidates`) and stops if there are none. The catalog is a price list, not live stock: which candidate is free is found by trying, within `launch_timeout`. A task file's `resources` can say the same (`accelerators`, `max_hourly_cost`, `any_of`, `ordered`).

## 10. Cost

Each cloud launch's cost, from the cloud's own records, is written to the launch ledger in the project's folder of the storage root: the one place costs are read from (per run and in total: tracking.md §7; the month's budget: §11). Every cloud run is in the ledger, so a run that logs nothing to MLflow (a data run) has its cost like any other. Code: `fieldbook/tracking/costs.py`, the ledger in `fieldbook/launch/budget.py`, each cloud's part in `fieldbook/clouds/`.

| File in `launches/` | Written by | Holds |
|---|---|---|
| `<run ID>.json` | The laptop, at launch | Cluster, cloud, author, agent, hourly price, time limit |
| `<run ID>.machine.json` | The machine, as its job starts | The cloud's ID for the machine, its type, region, node count (on AWS from the instance metadata service; on RunPod `RUNPOD_POD_ID`) |
| `<run ID>.ended` | The machine when its job is over; the laptop if the launch fails | Nothing: its time is the file's |
| `<run ID>.cost.<USD>` | A member's laptop, once the cloud's records are there | The cost is the name (`cost.none`: cannot be priced); the content says where it came from |

The files sit side by side with the cost in the name, so one listing gives every launch's state and cost and no file is read to sum a month.

- **When a launch is priced:** once its job is over: marked ended, or its run's record says it ended or stopped giving signs of life (runs.md §18), or its time limit is long past. Launches whose records are not there yet are tried again next time; one that fails is reported and skipped; one that never got a machine is marked `cost.none` and not tried again.
- **AWS (`aws-cloudtrail`):** the instance's `RunInstances` and `TerminateInstances` times from CloudTrail (free, 90 days, events arrive within about 15 minutes) × the on-demand price from SkyPilot's catalog × nodes; per-second, one-minute minimum. Start-up and teardown are included; disks are not. Multi-node runs are charged the head machine's time for every node.
- **RunPod (`runpod-billing`):** the amount billed for the pod (GPU, CPU, disk) from RunPod's billing API, read two hours after the run ends (hourly billing).
- **Who does it, and when:** members' machines (a viewer's is skipped), in the background during each `fieldbook run --on remote` and when `fieldbook log ui` opens, and before `fieldbook log costs` prints.
- **A copy in MLflow:** a run that logged to MLflow also gets the metric `fieldbook.cost_usd` and the tag `fieldbook.cost_basis` on its first top-level run, for the MLflow UI. Nothing reads it back.
- **Why not SkyPilot's totals:** `sky cost-report` keeps counting clusters that deleted themselves, since its local records never see the teardown (a 7-minute GPU run showed $0.42 instead of $0.06).
- **Why not MLflow as the record** (as it was): totals read from MLflow missed every cloud run that logged nothing there, while the budget counted them from the ledger; two sources that disagreed.

## 11. Safeguards

- **Dry run:** `fieldbook run --on remote --dry-run [--json]` (`cloud.plan`) says what a launch would do and launches nothing: the machines that fit with their prices, the time limit, the most the run can cost, the month's budget and what is left, whether the image is built, and the earlier run it repeats. What would stop the launch (no machine fits, a repeat without `--allow-repeat`, over a budget) is listed, not raised, and the exit code is 1. Nothing is built or recorded; the code snapshot is stored, as a launch would store it. It is how a person, or a coding agent asking for approval, sees the cost before spending.
- **A launch is watched from the laptop:** until `sky launch` returns, the launch timeout below runs on the laptop, and a laptop that sleeps does not count time or tear anything down until it wakes (seen in a check: an instance stayed 16 minutes). Once a run is launched, its limits are the machine's own (time limit, deletion after the job).
- **Launch time limit:** SkyPilot sets no time limit on image pulls or set-up, and its teardown applies only after a job runs, so a stuck launch would keep a paid machine running. `fieldbook` limits `sky launch` to `launch_timeout` and runs `sky down` on expiry or failure, reporting the stuck step. Image builds wait for the build too, so they get `launch_timeout` plus 30 minutes.
- **Time limit on every run:** the job is started under `timeout` on the machine (`timeout -k 60 <seconds> fieldbook run ...`: TERM to the job's process group, KILL a minute later), so the limit holds with the laptop closed; the cluster is then deleted as after any job. The limit is the shorter of `--max-hours` and what `budget_run_usd` buys on the run's machine, and 24 hours when neither is given (`budget.DEFAULT_HOURS`): a forgotten machine is the common way to lose money, and SkyPilot has no job time limit of its own.
- **Budgets** (`fieldbook/launch/budget.py`): `budget_run_usd` caps one run and `budget_monthly_usd` the project's month (UTC). Both are estimates made before launching, because a cloud's own cost arrives after the machine is gone (§10).

  | Step | What happens |
  |---|---|
  | Price | From SkyPilot's catalog, times nodes (`skypilot.candidates`; no credentials needed). With several candidate GPUs (§9) the dearest one's price is used, since any may be launched, so the limit is never too generous; `--max-price` narrows it. Within one candidate, a size without capacity may be replaced by the next, so the price is an estimate. |
  | Run cap | Time limit = cap ÷ price, less 10 minutes for start-up (`STARTUP`: launch and image pull are paid for too). A cap that buys under a minute is refused. |
  | Month cap | Spent so far + the most this run can cost (price × (limit + start-up)) must not exceed the cap, or the launch is refused with the numbers. No `--force`: the ways on are a shorter `--max-hours` or a larger budget in the project file. |
  | Spent so far | Read from the launch ledger (§10): a launch counts as its recorded cost if it has one, else price × time until it ended, or until now, never more than its limit. The launch is written before `sky launch`, and the machine marks its job over with a shell `trap` running `fieldbook launch-ended`. A machine that died without marking it counts up to its limit until it is priced. |
  | Unknown price | With a budget set, the launch is refused; without one it goes ahead with the time limit only. |

  - **Why a ledger:** a data run logs nothing to MLflow; a budget has to count those launches, and launches by every member.
  - **Project file only:** the two settings are refused in `.fieldbook/config.toml` and as `FIELDBOOK_*` variables (`PROJECT_ONLY`), so a person or a coding agent cannot raise the budget for one command; a change is a commit.
  - **A guardrail, not a wall:** an uncommitted edit of the project file raises it too, two members launching at the same moment can both pass the check, and anyone with the cloud's keys can start machines without `fieldbook`. The hard limit is the cloud's (AWS Budgets actions, a prepaid RunPod balance); the guide says so.
  - **Not built:** caps per member (`fieldbook log costs --total` shows spending per author).
- **A run outlives its machine:** its record, output, launch log, and the files it wrote are kept in the bucket as it goes (runs.md §18), so `fieldbook log wait`, `why`, `logs`, and `files` work after the cluster is deleted, from any member's machine. `sky logs` is no longer needed to follow a run.
- **Author:** the laptop's author is passed to the machine, so versions and runs are not recorded as `root`.
- **A fresh machine every run.** Keeping machines between runs and resuming a run under its old ID were built and removed: kept clusters caused stale code on reuse, teardown of shared clusters by failed launches, and cost splitting, and saved only start-up minutes.

## 12. Checks performed

| Check | Result |
|---|---|
| `--down` deletes the cluster after its job, laptop disconnected (AWS, `t3.small`) | Terminated about 1 minute after the job ended |
| A build machine builds and pushes to ECR with the registry cache | First build 40 s; second build on a fresh builder 4 s, every layer from the cache |
| CPU run end to end: build, run, dataset version to S3 | Passed. Build machine 3 minutes (cached rebuild); run machine 5 minutes. The version's lineage (run ID, code, seed) is visible from the laptop; the checkpoint folder is in the bucket |
| GPU run: `--gpus T4:1 torchrun --standalone --nproc-per-node 2` (`g4dn.xlarge`) | Passed: CUDA works, two DDP ranks start with identical weights from the run's seed. PyTorch image build 11 minutes (cold cache), run machine 7 minutes, about 5 of them pulling the image |
| Machine role | A machine with the run role wrote to the bucket as `assumed-role/fieldbook-run-…`, had no copied credentials, and deleted itself. The first attempt found that SkyPilot's teardown also needs `DescribeVpcs`, `DescribeSecurityGroups`, and `ModifyInstanceAttribute` |
| RunPod | A pod pulled the image from ECR with the 12-hour login, read S3 with the laptop's keys, and its cost was read from RunPod's billing |
| What is kept of a run (runs.md §18; AWS `t3.small`, 2026-10-11) | Passed, after two fixes the check found. The machine's signs of life, output pieces (every 30 s), joined output, files (`out/result.txt`, and one in `PLATFORM_OUTPUT_DIR`; one in `/tmp` was not kept, as intended), and end record reached the bucket; `fieldbook log wait`, `why`, `logs`, and `files` read them from the laptop. A task file's `setup` output is in the run's output (the machine runs it), not in the launch log. Found: under the run role, asking s3fs for a folder tries to create the bucket (nothing after the first sign of life was kept), and a watching loop saw its first listing for ever (a finished run reported as killed). |
| Time limit (`--max-hours 0.05`, AWS) | The machine stopped the job at 3 minutes (exit code 143), sent its last output, and wrote its end; `fieldbook log why`: "it reached its time limit" with the last lines. The cluster deleted itself. |
| GPUs by memory (`--gpus 16GB+ --max-price 0.30`, RunPod) | Four candidates listed ($0.25 to $0.28). RunPod had none in region after region; SkyPilot went through the candidates and regions by itself and launched an RTX A4500 after 5 minutes. (Its "failed to acquire" messages name a T4 throughout, a GPU RunPod's catalog does not have: a label from the list of 16 GB GPUs, not a machine it tried.) The run's output and files were kept as on AWS. |
| Cost recorded end to end (AWS `t3.small`, 2026-10-11) | The machine wrote which machine it was to the ledger; two minutes after the run ended, `fieldbook log costs` priced it from CloudTrail at $0.0017 (about 5 minutes at $0.0208 an hour) and wrote `cost.0.0017`; the per-run list, `--total` (under the author, by `claude-code`), and `fieldbook log query` showed the same number. The run logged nothing to MLflow. |
| Cost | AWS CloudTrail times × price checked against real records: $0.0017 for a `t3.small` check run |

Every check ran with an independent guard that would terminate any `fieldbook-*` instance after 12 minutes. It had to once, on 2026-10-11: the laptop slept in the middle of a launch, which stops everything that watches a launch from the laptop (§11), the guard included until it woke. Checks are run with the laptop kept awake (`caffeinate -i`). The run machines' bucket permissions can be tried without a machine, with a federation token limited to the run role's policy.

## 13. Risks

- **RunPod through SkyPilot:** pods use RunPod's GraphQL API, which retires in early 2027; SkyPilot's migration is pending. Keep SkyPilot current. Pods get the laptop's AWS keys (no IAM roles off AWS); temporary keys expire.
- **RunPod capacity:** the cheapest GPUs are sometimes unavailable in every region; allow several GPU types.
- **Image size:** CUDA PyTorch images are several GB; a first build takes about 10 minutes and a fresh machine pulls for several minutes.
- **No automatic recovery:** a hardware failure ends the run; a new run continues from its checkpoints (§8).
- **Machine roles:** a missing permission stops a machine from deleting itself. SkyPilot's teardown calls are covered and were checked with a real launch, but a SkyPilot upgrade could need more.
- **Registry passwords:** sent as SkyPilot secrets (all three `SKYPILOT_DOCKER_*` variables, as SkyPilot requires), so they stay out of the job's visible environment; SkyPilot still keeps the login with the cluster to pull the image. With ECR it is a 12-hour token; a run longer than that needs no new pull.
- **Members' AWS policy** has not been used by a real member identity yet (README.md §9).

## 14. Testing

Cloud paths are tested with fakes: moto for S3 and IAM, a fake `sky` executable, and a fake registry (`tests/launch/`, `tests/images/`, `tests/clouds/`). The real checks in §12 are repeated by hand after changes to launching, with the cheapest machines and the 12-minute guard. Budgets: time limits from the cap, the flag, and the default; the month's sum from recorded costs, ended, running, and forgotten launches; a refused launch's message; the two settings refused outside the project file; the limit lines of the machine's command run once by hand in an Ubuntu container (stopped with exit 124 at the limit, end noted both ways). GPU choices: names, memory sizes, and lists reach SkyPilot unchanged; the price is the dearest candidate's; no candidate stops the launch; the candidates for `24GB+` under $1 on RunPod listed once by hand from the real catalog (8 GPUs, $0.27 to $0.99). A dry run: its plan with fakes, and once against the real catalog and bucket (eight RunPod GPUs for `24GB+` under $1; nothing launched).
